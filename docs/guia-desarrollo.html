¿Por qué sin Docker?

Para tener Supabase dentro de tu computadora hace falta Docker, y Docker necesita permisos de administrador que solo IT puede dar. En su lugar usamos un proyecto gratis de supabase.com, Artisanal-ice-cream, como base de desarrollo. Ventaja extra: las dos computadoras (trabajo y casa) usan la misma base, con los mismos datos, sin preparar nada en cada una.

Usamos un solo proyecto, Artisanal-ice-cream, para todo: desarrollo, pruebas y, después de limpiarlo, producción. Así el segundo proyecto gratis queda libre para cuando lo necesites.

La limpieza del día del lanzamiento no se hace borrando registros a mano: el comando db:reset borra todo (datos, usuarios y tablas) y vuelve a crear la estructura desde las migraciones. Queda limpio por construcción. Los pasos están en el capítulo 13.

Reglas por compartir la base entre desarrollo y pruebas:
  1. Mientras programas solo (toda esta guía): puedes resetear la base y cambiar tablas cuando quieras.
  2. Cuando alguien esté probando la app publicada (parte 2): no uses db:reset, aplica cambios de tablas recién al unir a develop y avisa antes.
  3. Desde el lanzamiento, la base tiene ventas reales: db:reset queda prohibido y todo cambio de tablas se prueba con mucho cuidado (capítulo 13).

Si más adelante quieres un lugar aparte para probar, usas el segundo proyecto gratis (o Docker, si IT lo instala) cambiando solo variables, sin tocar el código.

La regla que hace todo fácil después: el código es el mismo en los tres entornos. Lo único que cambia son las variables de entorno (a qué Supabase se conecta) y dónde se publica. Por eso, cuando pagues Supabase Pro o cambies de hosting, no tendrás que cambiar código: solo valores de configuración.

Lo que hoy pruebas con npm run dev y Supabase local será lo mismo que se publicará. Los cambios de tablas viajan como migraciones (archivos SQL) con supabase db push, el mismo comando que ya usarás en desarrollo, y la app se publicará sola desde GitHub.

Muchos archivos "cambiados" que no tocasteFin de línea distinto. Verifica que exista .gitattributes y pídeme ayuda antes de hacer commit.
Cualquier otro errorCopia el mensaje completo de la terminal y pégamelo, diciendo en qué paso estabas.

# Heladería App

Sistema interno (no para clientes) de una heladería artesanal en Bolivia (moneda: Bs).
Usuarios: administración (la dueña) y colaboradores. Interfaz y mensajes en español.
Usar siempre el término "colaborador", nunca "trabajadora".

## Stack
React 19 + TypeScript + Vite · React Router · TanStack Query · Supabase (Postgres, Auth, RLS,
Edge Functions) · Dexie (cola sin conexión) · vite-plugin-pwa · Vitest + Testing Library ·
pgTAP · Playwright · Oxlint + Prettier + Husky.

## Entornos
Sin Docker (no hay permisos de administrador). UN SOLO proyecto Supabase: Artisanal-ice-cream
(enlazado con supabase link; variables en .env.local) para desarrollo, pruebas (rama develop) y
producción (rama main). El día del lanzamiento se limpia con db:reset y se rotan secret key,
contraseña de la BD y contraseña de admin. El código es el mismo en todos; solo cambian variables.
Comandos de base: db:push (aplicar migraciones), db:reset (borra TODO: solo antes del lanzamiento
y si nadie prueba; prohibido después), db:types, db:test, fn:deploy (--use-api, sin Docker).
Después del lanzamiento: revisar cada migración antes de aplicarla; las pruebas automáticas nunca
escriben en la base real.

## Reglas de la base de datos
- Todo cambio de estructura es una migración nueva en supabase/migrations. Nunca editar una
  migración ya aplicada en pruebas o producción.
- RLS activado en TODAS las tablas, con pruebas pgTAP en supabase/tests.
- Dinero: numeric(10,2). Fechas: timestamptz con default now(). Ids: uuid.
- Nombres de tablas y columnas en español, snake_case.
- Pedidos cancelados se BORRAN (no se guardan).
- Usuarios sin correo: usuario@heladeria.local. Sin registro público; las cuentas las crea la
  administración vía la Edge Function crear-usuario.

## Reglas del frontend
- Estructura por funcionalidad en src/features/<modulo>.
- Las pantallas no llaman a Supabase directo: usan funciones de datos del módulo.
- Variables VITE_ son públicas. La secret key nunca va en el frontend.
- Precios de vaso 5, 8 y 10 Bs; empanada 5 Bs. Cuatro temas: Clásico, Oscuro, Noche, Fresa y menta.
- Referencia funcional: Prototype/index.html. Guía de pasos: docs/guia-desarrollo.html.

## Forma de trabajo
- El usuario ejecuta los comandos y configura páginas web; Claude escribe el código y lo explica.
- Ramas feature/* → PR a develop → PR a main. Conventional Commits en español.
- Antes de dar algo por terminado: npm run lint, npm run test:run, npm run db:test.
