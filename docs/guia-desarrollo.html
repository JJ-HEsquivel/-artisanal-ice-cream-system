1. Cómo usar esta guía

  • Sigue los pasos en orden. Cada paso supone que el anterior salió bien. Si un "Comprueba" no da lo esperado, no sigas: mira el capítulo 14 o pregúntame pegando el error completo.
  • Tú haces lo que toca tu computadora o la web: instalar, ejecutar comandos, crear cuentas, configurar páginas. Yo hago lo que es código: crear carpetas y archivos, escribir y corregir el código, y explicarte cada cosa.
  • Al pedirme algo, copia el texto del recuadro naranja. Están escritos para que yo encuentre el contexto aunque abras una conversación nueva o estés en otra computadora: siempre mencionan el paso de esta guía, que estará guardada dentro del proyecto en docs/.
  • Después de que yo cree o cambie archivos, revisa lo que hice (VS Code marca los archivos cambiados en la pestaña Source Control) y pregúntame lo que no entiendas. Que el código funcione no basta: tienes que poder explicarlo.
  • Guarda en Git al final de cada etapa. Así puedes seguir desde la otra computadora y, si algo se rompe, volver atrás.
Terminal y PowerShell. La terminal es una ventana donde se escriben comandos de texto. En Windows, VS Code abre por defecto PowerShell. Todos los comandos de esta guía están escritos para PowerShell.
Carpeta actual (ruta). Los comandos se ejecutan "dentro" de una carpeta, que la terminal muestra a la izquierda del cursor. Cada paso de esta guía indica en un recuadro gris Dónde debe estar la terminal. Casi siempre es la carpeta del proyecto:

Si abres VS Code con la carpeta System-ice (File → Open Folder…), la terminal de VS Code (Terminal → New Terminal) ya se abre en esa ruta. Si alguna vez estás en otra carpeta, vuelve con:

cd C:\Users\Juan.Huanca\Desktop\Mokups\System-ice

Si un comando dice que no encuentra package.json, casi siempre es porque la terminal está en otra carpeta.

3. Etapa A · Preparar cada computadora

Antes de empezar en la computadora del trabajo: instalar WSL2 y Docker requiere permisos de administrador. Además, Docker Desktop es gratis para uso personal y empresas pequeñas, pero pide licencia pagada en empresas de más de 250 empleados o más de US$ 10 millones de ingresos. Si la computadora es de una empresa grande, consúltalo o usa Rancher Desktop (gratis), que también funciona con Supabase.

TÚ · TERMINAL (ADMINISTRADOR)A3. Instalar WSL2 y Docker Desktop

Esto necesita una terminal con permisos de administrador, que no es la de VS Code:

  1. Presiona la tecla Windows del teclado.
  2. Escribe powershell.
  3. En el resultado Windows PowerShell, a la derecha, haz clic en Ejecutar como administrador y acepta el aviso de Windows.

Se abre una ventana azul o negra que muestra esta ruta (es normal; para instalar no importa la carpeta):

PS C:\WINDOWS\system32>

Reinicia la computadora. Después: tecla Windows → escribe docker → abre Docker Desktop, acepta los términos (puedes saltar el inicio de sesión con Skip) y espera a que abajo a la izquierda diga Engine running.

WSL2 (Windows Subsystem for Linux). Permite correr Linux dentro de Windows. Docker lo usa porque los contenedores de Supabase son de Linux.

Recomendado: en Docker Desktop → Settings → General, desactiva Start Docker Desktop when you sign in si no quieres que consuma memoria siempre. Solo tendrás que abrirlo antes de trabajar.

Sobre proteger ramas: en GitHub gratis, las reglas que impiden subir directo a main solo funcionan en repositorios públicos. En privados requieren GitHub Pro (unos US$ 4/mes). Si lo pasas a privado, lo reemplazamos con disciplina: nunca trabajes directo en main y usa siempre Pull Requests, como indica esta guía.
GitHub es el centro de todo. Cloudflare Pages leerá este repositorio para publicar develop (pruebas) y main (producción), y GitHub Actions aplicará las migraciones a cada Supabase.

# Heladería App

Sistema interno (no para clientes) de una heladería artesanal en Bolivia (moneda: Bs).
Usuarios: administración (la dueña) y colaboradores. Interfaz y mensajes en español.
Usar siempre el término "colaborador", nunca "trabajadora".

## Stack
React 19 + TypeScript + Vite · React Router · TanStack Query · Supabase (Postgres, Auth, RLS,
Edge Functions) · Dexie (cola sin conexión) · vite-plugin-pwa · Vitest + Testing Library ·
pgTAP · Playwright · Oxlint + Prettier + Husky.

## Entornos
desarrollo = Supabase local (Docker) + .env.local · pruebas = rama develop · producción = rama main.
El código es el mismo en todos; solo cambian las variables de entorno.

## Reglas de la base de datos
- Todo cambio de estructura es una migración nueva en supabase/migrations. Nunca editar una
  migración ya aplicada en pruebas o producción.
- RLS activado en TODAS las tablas, con pruebas pgTAP en supabase/tests.
- Dinero: numeric(10,2). Fechas: timestamptz con default now(). Ids: uuid.
- Nombres de tablas y columnas en español, snake_case.
- Pedidos cancelados se BORRAN (no se guardan).
- Usuarios sin correo: usuario@heladeria.local. Sin registro público; las cuentas las crea la
  administración vía la Edge Function crear-usuario.

## Reglas del frontend
- Estructura por funcionalidad en src/features/<modulo>.
- Las pantallas no llaman a Supabase directo: usan funciones de datos del módulo.
- Variables VITE_ son públicas. La secret key nunca va en el frontend.
- Precios de vaso 5, 8 y 10 Bs; empanada 5 Bs. Cuatro temas: Clásico, Oscuro, Noche, Fresa y menta.
- Referencia funcional: Prototype/index.html. Guía de pasos: docs/guia-desarrollo.html.

## Forma de trabajo
- El usuario ejecuta los comandos y configura páginas web; Claude escribe el código y lo explica.
- Ramas feature/* → PR a develop → PR a main. Conventional Commits en español.
- Antes de dar algo por terminado: npm run lint, npm run test:run, npm run db:test.
